# webnovel-writer v2.0 完整更新总结

> **主题**: 系统化约束执行，从"记录约束"升级到"强制执行约束"  
> **发布日期**: 2026 年 4 月 6 日  
> **核心改进**: 新增 3 个 Agent + 4 个参考文档 + 3 个 Python 框架

---

## 一、问题背景

### v1.0 存在的问题

| 问题 | 表现 | 影响 |
|-----|------|------|
| **约束执行弱** | 创意约束写在文档里，但实际写作不遵循 | AI 味依旧、剧情平庸 |
| **无执行监控** | 没有"检查点"验证是否按计划执行 | 发现问题太晚，修改成本高 |
| **缺约束日历** | 反套路何时激活、怎样激活无明确规划 | 约束激活时间随意，效果差 |
| **无冲突处理** | 约束与大纲冲突时无预案 | 容易出现"约束被大纲压倒"的情况 |
| **缺数据流** | 约束信息在 Agent 之间流转不清晰 | Agent 协作混乱，效能低 |

### v2.0 解决方案

```
v1.0: 约束 (文档) → 不遵循 → 定稿检查 (太晚)

v2.0: 约束 (文档) → 日历 (何时) → 执行包 (怎样) → 50% 检查 (及时)
      ↓                    ↓              ↓
      (约束继承)    (context-agent v5.5.1)  (execution-package-checker)
                                            ↓
                                    100% 定稿检查 (四维审计)
```

## 三、工作流变化

### v1.0 工作流

```
webnovel-plan → webnovel-write → webnovel-review → 定稿

(19 个 Agent，但约束执行链路不清晰)
```

### v2.0 工作流

```
webnovel-plan
  ├─ Phase 2.5: 约束加载检查 ⭐ NEW
  └─ Phase 7: constraint-inheritance-manager 生成日历 ⭐ NEW
             + 自动标注细纲 Frontmatter

webnovel-write
  ├─ Step 0.5: context-agent v5.5.1 融合约束到执行包 ⭐ UPDATED
  ├─ 50% 进度: execution-package-checker 检查 ⭐ NEW
  │   ├─ ≥70% → 继续
  │   ├─ 50-70% → 继续但标记风险
  │   └─ <50% → 立即回修
  └─ Step 1-4: 完成写作

webnovel-review
  ├─ Phase 1: chapter-audit-checklist 四维审计 ⭐ NEW
  │   ├─ PASS → 定稿
  │   └─ FAIL → 回修 Phase 2-N
  └─ 每 5-10 章: constraint-inheritance-manager 周期审计 ⭐ NEW
```

## 五、快速开始指南

### 👤 对不同角色的使用说明

#### 角色 1: 项目规划者 (大纲作者)

**在 webnovel-plan 阶段**:

1. ✅ 完成大纲规划 (Phase 1-6)
2. 运行 `constraint-inheritance-manager --action init`
   - 自动生成 `.webnovel/constraint_activation_calendar.md`
   - 查看约束激活日历是否合理 (反套路布局、三轴深化等)
3. 如有调整，参考 `constraint-conflict-detection.md` 处理冲突
4. 进入 Phase 7.5，细纲自动标注约束字段

**检查清单**:
- [ ] 约束激活日历已生成并评审
- [ ] 3-5 条反套路分布合理 (非堆砌)
- [ ] 三轴混搭计划清晰 (早期铺垫→中期激活→后期爆发)

---

#### 角色 2: 写手/创作者 (章节作者)

**在 webnovel-write 阶段**:

1. 打开第 N 章的细纲，注意新增的 Frontmatter 约束字段
   ```yaml
   constraints:
     dominant_constraint: "反套路 #3 (反派智商在线)"
     constraint_strength: "strong"
     # ... 更多字段
   ```
2. Step 0.5 后，阅读生成的执行包，特别注意"创意约束执行"板块
3. 按执行包指导写作
4. **50% 进度时**，运行 `execution-package-checker --chapter XXXX --checkpoint 50`
   - 获得符合度报告
   - 根据建议修改 (若符合度 < 50%) 或继续写 (≥ 70%)
5. 100% 完成后，继续到 webnovel-review

**关键提示**:
- ⚠️ 不要忽视 "创意约束执行" 板块的约束要求
- 💡 若感觉"机械感"，参考现有 AI-trace-checker 优化风格
- 🎯 反套路是为了"读者惊喜"，不是"机制复杂"

---

#### 角色 3: 审稿人/编辑 (质检者)

**在 webnovel-review 阶段**:

1. 收到完整章节后，不要直接审稿，先运行 `chapter-audit-checklist --chapter XXXX`
   - 自动生成四维清单
   - 快速定位问题
2. 根据清单中的"关键项"进行人工审稿
   - 关键项必须全部 ✅ PASS
   - 建议项 ⚠️ 可讨论
3. 若有关键项 FAIL，打回作者修改，修改后重新运行清单
4. 定稿前，运行 `constraint-inheritance-manager --action audit --start X --end Y` 检查 X-Y 章的约束执行总体情况

**常见决策**:
- PASS → 直接定稿
- ⚠️ WARNING → 可讨论修改优先级
- FAIL → 必须修改，重新审查

## 七、常见问题 (FAQ)

### Q1: v2.0 必须要用 Python 脚本吗？

**A**: 不一定。
- 每个 Agent 都有"Markdown 版本"的完整说明
- 可以手动执行 (但慢且易出错)
- 推荐用 Python 脚本 (快速、准确，有日志)
- **建议**: 先手动执行 1-2 章理解逻辑，然后用脚本

---

### Q2: 如果我的 idea_bank.json 还是 v1.0 格式怎么办？

**A**: 需要升级。
1. 读 `idea-bank-complete-schema.md`，了解新字段
2. 在现有 idea_bank.json 中添加：
   - `constraint_activation_schedule` (新)
   - `cool_point_system.white_list / black_list` (新)
   - `enforcement_status` (新)
3. 运行 `constraint-inheritance-manager --action init` 验证格式正确

**注**: 升级脚本见 PYTHON_SCRIPT_FRAMEWORKS.md

---

### Q3: 我已经写了 50 章，现在升级 v2.0，需要回修吗？

**A**: 看具体情况。
- **已经完全遵循大纲的** → 直接运行 `constraint-inheritance-manager --action audit --start 1 --end 50` 检查约束执行情况，可能无需大改
- **有明显约束缺失的** → 建议在"第二稿"时系统修复
- **想从现在开始执行** → 第 51 章开始严格使用 v2.0 流程

**推荐**: 运行审计，看看有多少约束被激活，再决定

---

### Q4: execution-package-checker 在 50% 时说 FAIL，怎样快速恢复？

**A**: 参考 `execution-package-checker.md` 中的"FAIL 恢复流程"：
1. 判断符合度多少 (< 30% / 30-50% / 50-70%)
2. 选择对应的恢复策略 (完全重写 / 局部补充 / 修改替换 / 标记风险)
3. 修改后重新检查，直到通过

**快速路** (如果很急):
- 符合度 45% → 策略 B (补充关键缺失项) + 策略 D (标记其他风险) + 继续写
- 预计时间: 30 min + 继续写

---

### Q5: 我的 chapter-audit-checklist 四维审计 FAIL 在"约束激活度"，怎么改？

**A**: 
1. 查看"约束激活度"清单中哪些项失败
2. 对标 `constraint_activation_calendar.md`，知道本章应激活哪个反套路
3. 参考该反套路在 `constraint-inheritance-manager.md` 中的"激活建议"
4. 在正文中补充具体的表现 (对话、行为、心理)
5. 重新运行清单

**例**: 
- 反套路 #3 (反派智商) 未激活 → 补充反派的完整计划细节 (+500 字左右)
- 三轴体现缺失 → 在情节中暗示赛博修真的冲突 or 寿命修炼的代价

---

### Q6: 如果约束与大纲真的冲突了，怎么办？

**A**: 参考 `constraint-conflict-detection.md`：
1. **识别冲突类型**: A (约束 vs 大纲) / B (约束 vs 约束) / C (约束 vs 气质)
2. **计算侵蚀指数**: (计划 - 实际) / 计划，是否 > 30%
3. **选择处理方法**:
   - 修改大纲 (优先)
   - 调整约束表现 (次优)
   - 放弃约束 (最后手段)
   - 添加补充背景 (解释原由)

**不要**: 直接删除约束、偷偷改大纲而不记录

---

### Q7: 三个新 Agent (约束继承、符合度检查、四维审计) 都要用吗？

**A**: 是的，都建议用：
- **constraint-inheritance-manager** (必须) → 核心，没有它后续无法进行
- **execution-package-checker** (强烈建议) → 及时发现问题，节省后期修改时间
- **chapter-audit-checklist** (必须) → 最后的质检门槛，保证质量

**不缺任何一个，否则链路断裂。**

---

### Q8: context-agent 升级到 v5.5.1 有什么变化？

**A**: 只有输出变化，输入和流程不变：
- **新增输出**："创意约束执行" 板块 (第 8 板块)
- **包含内容**: 本章主导约束、三轴检查、反套路清单、镜像对抗建议
- **对写手影响**: 需要在"创意约束执行"板块中查看约束要求，融合到创作中

**实现**: 在 Phase 0.5 中读取约束日历，在 Phase 3-7 中融合到执行包，Step 1-4 时供写手参考

---

### Q9: 每 5 章的周期审计具体做什么？

**A**: 运行:
```bash
constraint-inheritance-manager --action audit --start 1 --end 5
constraint-inheritance-manager --action audit --start 6 --end 10
# ... 以此类推
```

输出报告包含：
- 本 5 章内约束激活是否按计划
- 三轴混搭是否平衡
- 镜像对抗的深化度
- 风险预警 (有无偏离)

**决策**: 
- ✅ 正常 → 继续
- ⚠️ 有偏离 → 调整后续计划
- ❌ 严重偏离 → 考虑修改约束或大纲

---

### Q10: 这样做会不会让创作变得"僵化"或"机械"？

**A**: **不会，反而相反。**

**原理**:
- v1.0: 约束在文档里 → 写手可能忘记 → 最后才发现 → 补救有限 → 被迫"舍弃约束为了急稿"
- v2.0: 约束在日历里 + 执行包里 + 每章标注里 → 写手时刻意识 → 提前融合到故事中 → 约束与故事水乳交融

**"机械感"的根源不是约束本身，而是执行不当**。正确的做法是：
1. 在细纲级别就规划好约束的表现形式
2. 在初稿中自然融合
3. 在修稿中调整细节，隐藏"设计痕迹"

**关键工具**: 配合 `ai-trace-checker` 和 `writing-style-guide` 隐藏机械感
